## B. Findings

```
Severity: MEDIUM
File/migration: 0007_visits_followups_deals_documents.sql
Problem: visits.customer_id, visits.property_id, and follow_ups.customer_id were
  ON DELETE CASCADE.
Why it matters: Hard-deleting a customer or property (a raw SQL DELETE, an admin
  mistake, or a future "delete" UI action) would silently destroy visit and follow-up
  history — the spec explicitly calls for archive/deactivate behavior over destructive
  loss of business history for entities like this.
Recommended fix: Changed to ON DELETE RESTRICT (applied in 0010). Deleting a customer
  or property that has visits/follow-ups now fails with a clear FK error instead of
  quietly cascading; the application should use status changes (property SOLD/RENTED,
  customer lead_status INACTIVE) as the real lifecycle mechanism, not hard delete.
  leads.customer_id intentionally stays CASCADE — a lead is a raw enquiry-event log
  with no independent meaning once its customer is gone, unlike a scheduled visit or
  follow-up task.
Status: FIXED and verified live — deleting a property with a visit now raises
  "violates foreign key constraint" instead of succeeding.
```

```
Severity: LOW
File/migration: 0009_public_views.sql (properties_within_radius)
Problem: No upper bound on radius_km or limit, and no validation on lng/lat ranges.
Why it matters: A caller (even anon) could request an unbounded radius or a very large
  page size. At current data volume this is harmless, but it's the kind of unbounded
  input that stops being harmless as the table grows into the thousands, and invalid
  coordinates would silently produce a meaningless distance rather than a clear error.
Recommended fix: Clamped radius to 0.1–50km and limit to 1–50 rows server-side, and
  reject out-of-range longitude/latitude with an explicit error (applied in 0010).
Status: FIXED and verified live — an absurd radius/limit request now returns the
  clamped, correct result set (12 rows, not an unbounded scan), and an invalid
  longitude (999) is rejected with "A valid location is required".
```

```
Severity: INFORMATIONAL (no fix needed)
File/migration: n/a — test-harness artifact, not a schema issue
Problem: The audit script's first pass showed "FAIL: anon UPDATE staff_profiles
  succeeded" and "FAIL: STAFF DELETE a deal succeeded".
Why it matters: Explaining this so it isn't mistaken for a real hole. Supabase grants
  anon/authenticated blanket table-level INSERT/UPDATE/DELETE privileges by default and
  relies entirely on RLS to filter which rows are actually affected. Both statements
  "succeeded" with rowCount = 0 — RLS correctly filtered every row before any write
  could land, which is the expected behavior, not a bypass. Confirmed by checking
  rowCount directly (0 in both cases) and by the STAFF admin-only test correctly
  showing rowCount = 1 when the same delete was run as ADMIN.
Status: No fix needed. Test harness corrected to assert on rowCount instead of
  thrown/not-thrown for UPDATE/DELETE checks, to avoid this false positive in future
  runs.
```

## C. Portability verdict

The schema can migrate to standard/self-hosted PostgreSQL with reasonable effort. Breakdown:

**Portable** (plain PostgreSQL/PostGIS, no Supabase dependency):
- All business tables, enums, constraints, indexes, triggers (`set_updated_at`, code-generation
  functions).
- `create_public_lead()`, `properties_within_radius()` — standard `plpgsql`/`sql` functions,
  PostGIS-only geography use.
- `public_properties` view — a plain view, no Supabase-specific construct.

**Supabase-specific** (by necessity, isolated and documented in `docs/ARCHITECTURE.md` §6):
- `staff_profiles.user_id → auth.users(id)` — ties staff identity to Supabase Auth's user table.
- RLS policies call `auth.uid()`, which reads `request.jwt.claim.sub` — a PostgREST/Supabase
  convention for turning a JWT into a Postgres session variable.
- `is_staff()`/`is_admin()`/`current_staff_role()` wrap `auth.uid()`, so they inherit the same
  dependency.

**Future migration considerations**:
- Moving off Supabase means replacing `auth.users` with another identity table and replicating
  how `auth.uid()` gets populated per request (any JWT-aware Postgres proxy, or an app-level
  equivalent) — a bounded, well-known problem, not a rewrite of business logic.
- No table, function, or trigger outside `staff_profiles`/the `is_*()` helpers references
  Supabase at all — properties, customers, leads, visits, follow_ups, deals, documents are 100%
  portable as-is.
- Supabase Storage is referenced only as a `storage_path` string column (metadata), never as a
  live dependency in schema — swapping storage providers later requires no schema change.

**Verdict: acceptable.** The coupling is exactly where the spec asked it to be (auth + RLS
identity), and nowhere in the actual property/lead/visit/deal domain model.

## D. Scalability verdict

- **1,000 customers**: trivially fine. Indexed phone/email/name lookups, `EXPLAIN` already
  confirms index scans (not seq scans) on the phone-dedup path.
- **10,000+ customers**: still fine. All hot paths (dedup-by-phone, property filters, radius
  search) are backed by real indexes (`idx_customers_phone` on the normalized-phone expression,
  `idx_properties_geog` GiST index, per-column indexes on status/type/locality). No query in the
  schema does a full-table fetch to filter/sort in application code.
- **Substantially larger datasets (100k+)**: the design still holds structurally (proper indexes,
  server-side filtering, PostGIS radius search bounded to ≤50km/≤50 rows per call as of this
  audit). At that scale the practical limits become Supabase free-tier resource caps (connection
  count, compute), not the schema — exactly the tradeoff the spec accepted for MVP scope.
- **~100 concurrent users**: the session-pooler connection path (already required for this
  environment's IPv6 limitation) is the right pattern here too — it's built for exactly this
  kind of moderate concurrent load without needing a custom pooling layer.

No microservices/Redis/Elasticsearch/sharding needed or recommended at this stage — consistent
with the spec's explicit instruction not to over-engineer.

## Live test results (summary)

All of the following were verified against the actual Supabase database, not inferred from
migration files:

- Anon cannot SELECT `customers`, `leads`, `customer_roles`, `visits`, `follow_ups`, `deals`,
  `documents`, `staff_profiles`, or the raw `properties` table — 0 rows every time.
- Anon cannot INSERT into `customers`, `leads`, `customer_roles`, or `properties` — RLS policy
  violation on every attempt.
- `public_properties` structurally lacks `owner_name`, `owner_phone`, `owner_email`,
  `negotiation_min`/`max`, `internal_notes` — selecting them raises "column does not exist",
  confirmed live.
- `property_media` is visible to anon only for properties with `status = 'AVAILABLE'`.
- An authenticated user with **no** `staff_profiles` row gets exactly the same (zero) access as
  anon to internal tables — having a Supabase Auth account alone grants nothing.
- A `STAFF` user can read/manage customers, properties, and deals, but cannot delete a deal
  (admin-only) and cannot escalate their own role (blocked by the `guard_staff_profile_self_update`
  trigger).
- An `ADMIN` user can delete a deal (verified a real row was removed, then rolled back).
- `create_public_lead()` dedups correctly by normalized phone: two submissions with the same
  number (formatted differently) produce exactly **one** customer row, **two** lead-interaction
  rows (property context preserved on each), and the name updates only when the new one is
  longer/more complete — verified with a real committed transaction, then cleaned up.
- No information leakage: both branches (new customer vs. existing customer) return the identical
  `{lead_id, customer_code}` shape, and no phone/customer data is echoed back to the caller.
- Normalized-phone lookups and radius search both use their indexes (`EXPLAIN` confirms
  `Index Scan`, not `Seq Scan`).
